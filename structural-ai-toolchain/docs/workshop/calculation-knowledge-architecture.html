Problem

  • Thousands of calculation files on servers and project folders, in many formats.
  • The same checks are rebuilt on every project; copies diverge, corrections do not propagate.
  • Origin, author, code edition and quality are often unknown.
  • Spreadsheets are readable but hard to version and reuse; code is reusable but does not read as a calculation.

Objective

An ingestion pipeline that retrieves every calculation we own, distils the design logic inside it into modular calculation objects, and consolidates those objects into a unified design logic for each topic of structural engineering. The result is a version-controlled knowledge base that maps what we know and where the gaps are, produces tested tools and self-documenting calculations, and improves with every project that uses it.

What has to be built, and how

Ingestion · 1

Retrieval and curation

An agent that scans the company servers, catalogues every calculation file and curates what enters the pipeline.

  • Tags each file: project, department, author, date, code, design topics
  • Curation criteria: relevance, completeness, known origin, current code edition
  • New files and new calculations enter through the same route

How broad should the scraping be, and how much should be curated by hand?

MediumKnown technology; access rights, NDAs and volume are the work.

Conversion

A parser that converts each format into machine-readable content.

  • Readers exist for Excel, Mathcad, Python, Jupyter and MATLAB
  • Recalculated values compared with the original before acceptance

Distillation · 3

Decomposition

An AI that reads a calculation, distils its logic into modular calculation objects and maps each object to a topic of structural engineering.

  • Design logic separated from project data
  • One taxonomy: topic, element, code clause
  • A topic map: what is covered, what is missing, where sources are many

How reliable is the AI at reading engineering logic?

What granularity: one equation, one clause or one design check?

Very highTurning an existing file into logic requires engineering understanding.
Distillation · 4

Consolidation by consensus

Deterministic acceptance criteria that let the AI judge what enters the unified design logic.

The AI cannot rely on its own judgement to accept or reject engineering logic. It needs a rule that is the same every time. The proposed rule is consensus between independent implementations, similar to a distributed ledger, which accepts an entry only when independent parties agree. Each calculation object is executed over a common parameter domain. Where independent sources agree within a defined tolerance, there is nothing to debate and the logic is merged. Only disagreement needs an engineer.

What tolerance, and how many agreeing sources, constitute consensus?

What level of human supervision does each stage require?

ConsensusIndependent sources agree within tolerance over the whole domain. Merged automatically.
Partial consensusAgreement on part of the domain. Common logic merged; the divergence isolated as a branch for review.
No consensusAdjudication by an engineer. Valid alternative methods retained side by side.
HighA new method; tolerances and test domains have to be defined per topic.
Knowledge base · 5

Object generation

An LLM that turns each unified design logic into a tested Python calculation object.

  • Written from a structured specification per object
  • Benchmarked against the original files and other checked projects
  • Engineer approves before release

How do we set up the benchmarks?

MediumCode generation is mature; the benchmarks are the work.
Knowledge base · 6

Repository and search

A secure, version-controlled knowledge base with an AI-curated search engine.

  • Finds the relevant calculation object for a design task
  • Checks every new calculation: already covered, an extension, or a new design topic
  • Versions, access rights, approvals and written rules for contributors and the AI

In this way most topics of structural engineering can be mapped.

Use and maintenance · 7

Self-documenting calculations

A framework that makes every Python calculation print itself as a human-readable calculation document, at the same quality as our existing calculations.

  • Each step typeset: equation, substituted values, result, clause
  • Produced by the same run that computes the numbers
  • Company template; QA status on the document

How do we make modular code human-readable?

Very highReadability and modularity pull in opposite directions.
Use and maintenance · 8

Maintenance

Auditing of the knowledge base, scheduled health checks, and a route for corrections and new components.

  • Health checks re-run every benchmark
  • Changes pass consolidation and testing again
  • Maturity: harvested, converted, consolidated, verified, approved

How many people and departments should be involved?

LowProcess and ownership more than technology.

Worked example: four bridge calculations

Four files from four bridge projects. They overlap only partly and use different national annexes.

FileFormatProjectBendingShearNational annex
APython scriptBridge 1✓✓DK
BJupyter notebookBridge 2✓–UK
CExcel workbookBridge 3–✓DK
DMathcad sheetBridge 4✓✓NO
  1. 1
    Ingestion

    The four files are retrieved, tagged and converted. Recalculated values match the originals.

  2. 2
    Decomposition

    Six calculation objects: three for bending (A, B, D) and three for shear (A, C, D).

  3. 3
    Consensus on bending

    National annex coefficients are separated out as parameters. The three objects then agree within tolerance over the whole domain, giving one unified bending object with the national annex as an input.

  4. 4
    No consensus on shear

    The objects assume different lever arms: one uses an approximate value, the other calculates it precisely. The rest of the logic agrees and is merged; an engineer decides which lever arm is correct.

  5. 5
    Object generation

    Python objects are generated and benchmarked first against the four original files, then against other checked bridge projects. They are released as version 0.1.

  6. 6
    Use

    An engineer on a fifth bridge searches for shear design. The search engine returns the unified object; the engineer runs it and receives a self-documenting calculation.

  7. 7
    Maintenance

    A torsion calculation is submitted. The search engine identifies it as a new component, not yet covered. It passes the consensus rules and the benchmarks and is released as version 0.2. Every health check re-runs the benchmarks of all four projects.
