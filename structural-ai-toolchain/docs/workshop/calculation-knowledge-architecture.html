Calculation Knowledge Architecture

StatusFor discussion
RevisionB
Date2026-10-13

Problem

  • Thousands of calculation files on servers, project folders and personal drives, in many formats.
  • The same design checks are rebuilt on every project; copies diverge and corrections do not propagate.
  • Origin, author, code edition and quality are often unknown.
  • Excel and Mathcad are readable but hard to version, test and reuse; code is reusable but does not read as a calculation.

Objective

Collect every calculation we own, extract its design logic, and consolidate it into one version-controlled library that maps structural engineering topic by topic. Tools and calculation reports are produced from that library, and every use feeds corrections back into it.

  • A catalogue of all calculation files and the topics they cover, including gaps.
  • One unified, modular design logic per topic; alternative methods kept where they are valid.
  • Calculation reports generated from the code, as readable as a Mathcad sheet.

Stages: what has to be solved

1

Retrieval and identification

Find and catalogue every calculation file. New files and new calculations enter the same way.

To solve
  • Crawling servers and project folders
  • Tagging: project, department, author, date, code, topics
  • Duplicates and versions
  • Intake for new files
Blockers
  • Privacy, NDAs
  • Access rights
  • Volume
  • Poor metadata
Options
  • Read-only crawler with AI classification
  • Project register for metadata
  • Pilot on one topic first
Selection criteria
Relevant design topicCurrent code editionComplete: inputs, checks, resultsKnown originChecked or used on issued workNot a duplicateFills a gap in the topic map
2

Conversion to machine-readable format

Translate every format into one structured representation, checked against the original.

To solve
  • A converter per format
  • Capture the logic, not only the results
  • Recalculate and compare with the original
  • Link back to the source
Blockers
  • Choice of conversion tool
  • Closed and legacy formats
  • Scanned hand calculations
  • Conversion reliability
Options
  • Existing readers for each format
  • AI-assisted interpretation, verified by recalculation
  • One common intermediate format
Formats in scope
ExcelMathcadPythonJupyterMATLABSMathPDF and scanned hand calculations
Target format (open)
Python (working assumption)Structured data (JSON)Database (SQL)Notebooks
3

Decomposition and topic mapping

Split each file into modular units of design logic and place them on a map of structural engineering topics.

To solve
  • Separate design logic from project data
  • Unit size: equation, clause or design check
  • Classification: topic, element, code clause
  • Topic map with coverage and gaps
Blockers
  • Several topics mixed in one file
  • Inconsistent notation
  • Defining the taxonomy
  • Misclassification
Options
  • Dependency analysis of formulas
  • AI classification against a fixed taxonomy
  • Eurocode notation as the naming standard

Every topic found is mapped, whatever the accuracy of its source. One unverified wind or foundation sheet still marks a topic as present and to be developed. Topics with many sources, such as bending design, are where consolidation pays off; topics with none are visible gaps.

4

Consolidation

Merge units that cover the same design concept into one unified logic, according to how closely they agree.

High agreementSame results on common test cases. Cluster and merge; record minor parameter differences.
Partial agreementDifferences in parameters, assumptions or algorithm. Review the differences.
Strong disagreementError or a different assumption. An engineer decides; valid alternative methods are kept side by side.
To solve
  • Common test cases for comparison
  • Agreement thresholds
  • Keeping valid alternatives
  • Recording every decision
Blockers
  • Reviewer capacity
  • Disagreement is not proof of error
  • Differing code interpretations
  • Low-quality early sources
Options
  • Supervision set by agreement: none, partial, full
  • Benchmark library
  • One structured specification per module (Markdown template)
5

Central repository

Store the unified logic and its code: secure, versioned, with written rules for contributors and for the AI.

To solve
  • Version control
  • Access control
  • Rules for AI and contributors
  • Automatic tests on every change
Blockers
  • IT security approval
  • Data residency
  • Cost, licences
  • Governance overhead
Options
  • Enterprise GitLab
  • Company-hosted AI
  • Released library versions for project use
6

Library and tools

Search by design topic and assemble project calculations from verified modules.

To solve
  • Search by topic, code and element
  • Each module shows its specification, code, sources and QA status
  • Tools that reference modules instead of copying them
  • Validity limits
Blockers
  • Adoption
  • Choice of user interface
  • Use outside the validity range
Options
  • Web catalogue
  • Excel or notebook front end calling the library
  • Batch runs with the governing case reported
7

Reports and QA

A calculation report produced from the same run as the numbers, then checked.

Main open problem

Code is modular and efficient but does not read as a calculation. The report must be generated from the executed code, one-to-one: typeset equations in symbolic form, then with values substituted, then the result and the clause reference, as in Mathcad. It must not be written separately afterwards.

To solve
  • Report generated from the executed code
  • Typeset equations: symbolic, substituted, result
  • Company template
  • QA status shown on the report
Blockers
  • Readability versus modularity
  • Acceptance by checkers and clients
  • Liability, sign-off
Options
  • Symbolic rendering libraries
  • Literate documents (text and live code) to PDF
  • Automated checks, then a human checker
8

Feedback

Every finding from use becomes a reviewed change and a new version.

  1. Harvested
  2. Converted
  3. Consolidated
  4. Verified
  5. Approved
To solve
  • Reporting issues from a report back to its module
  • Same review as any other change
  • Notifying affected projects
  • Tracking maturity
Blockers
  • Time to report
  • Errors in issued work
  • Ownership
Options
  • Issue log per module
  • Module owners per discipline

Worked example

Four calculations of a reinforced concrete beam to EN 1992-1-1, from four projects and four departments.

FileFormatOriginTopics found
APython scriptBridges, project 1Moment resistance, shear, crack width
BJupyter notebookBuildings, project 2Moment resistance, shear, crack width
CExcel workbookIndustry, project 3Moment resistance, shear, crack width
DMathcad sheetFoundations, project 4Moment resistance, shear (strut-and-tie), crack width, pile cap
  1. 1
    Retrieval and identification

    Found on four project servers and tagged with project, department, author, date, code edition and topics. All four meet the selection criteria; D is marked as unchecked.

  2. 2
    Conversion

    Each file is converted to the common machine-readable format. Recalculated values match each original.

  3. 3
    Decomposition and topic mapping

    Each file is split into units for moment resistance (6.1), shear (6.2) and crack width (7.3.4). D also contains a pile cap design, so foundation design is added to the topic map, as unverified.

  4. 4
    Consolidation

    All units are run on the same test cases.

    • agreeMoment resistance: all four within 1 %. Merged.
    • disagreeCrack width: A, B and C agree; D is 40 % higher. An engineer finds that D assumes long-term loading. Recorded as an input parameter, not an error.
    • alternativeShear: A, B and C agree; D uses strut-and-tie for deep beams. Kept as a second method with its own validity range.

    The AI writes one structured specification per topic (Markdown template: scope, inputs, equations, clauses, validity limits, sources, test cases). An engineer reviews it.

  5. 5
    Central repository

    The specification is implemented in Python, tested against the test cases and committed to GitLab as version 0.1, status "consolidated".

  6. 6
    Library and tools

    An engineer searches for "shear design, RC beam" and finds the module with its specification, code, sources, test results and QA status.

  7. 7
    Reports and QA

    The engineer runs it with project inputs. The same run produces the calculation report with typeset equations, substituted values, results and clause references. A checker reviews and approves it.

  8. 8
    Feedback

    The checker adds a national annex parameter and supporting documentation. The change is reviewed, the tests pass, and the module becomes version 0.2. The next project starts from 0.2.
