Workshop basis · structural engineering

Calculation Knowledge Architecture

From scattered calculation files to one verified, version-controlled body of design knowledge that produces readable, checkable calculations.

StatusFor discussion
RevisionA
Date2026-10-13
ScopeAll disciplines

Part 1

The problem

Our design knowledge exists, but it is spread across thousands of calculation files on different servers, project folders and personal drives. The same check is re-built project after project, in different formats, by different people, with different mistakes. Nobody can say which version is correct, who wrote it, or which projects relied on it.

Scattered and duplicated

Ten shear design sheets for one code clause, each copied from an older project and edited slightly. Corrections made in one copy never reach the others.

Unknown provenance and quality

Authors have left, file dates are overwritten on copy, code editions and national annexes are not stated. A sheet that looks right may carry a unit slip or a superseded formula.

Readable or reusable, never both

Mathcad and Excel show the calculation to a checker but are hard to version, test and reuse. Code is modular and testable but does not read like a calculation.

Part 2

The objective

Build a system that finds every calculation we own, extracts the design logic inside it, and consolidates that logic into one single source of truth: one verified, modular, version-controlled master for each design concept.

The master grows over time. At the start it will contain unverified and inconsistent material. Each new file adds only what is new or corrects what is wrong; mistakes are rejected and flagged; every change is reviewed and tested against benchmark cases. From this master we assemble project tools whose reports read like a Mathcad sheet and are produced directly from the logic that computed the numbers.

  • A catalogue of every calculation file, with where it came from, who wrote it and what it does.
  • One master module per design concept (e.g. shear resistance of RC members to EN 1992-1-1), with legitimate variants kept side by side.
  • Every change to a master traceable, reviewed and re-tested automatically.
  • Project tools assembled from verified modules instead of copied sheets.
  • Calculation reports a checker can follow line by line, generated from the executing logic.
  • A feedback route so errors found on projects correct the master once, for everyone.
AI proposes, engineers decide

Automation does the volume work; changes to approved design logic need human approval.

Every number traceable

From any reported value back to the module revision, the code clause and the source files it was derived from.

Nothing changes silently

Conflicts and errors are flagged and kept on record, never quietly absorbed or discarded.

The stages in detail

Every stage below is open for debate. The lists are a starting point for the workshop, not decisions.

1

Layer 1 · Retrieval and identification

Discovery and cataloguing

↑ overview

An agent with read access searches every server, project folder and document system, and builds a catalogue of every calculation file regardless of its quality. For each file it records where it was found, who created it, when, for which project and department, and what the file calculates. Engineers can also submit files from new projects, or calculations written from scratch, through the same entry point.

InputCalculation files wherever they are stored, plus new submissions
OutputA catalogue: one record per file with provenance and a content description

What has to be solved

  • Locate calculation files across file servers, project folders, document management systems and personal drives.
  • Recognise every file type, including old and macro-enabled formats.
  • Record provenance: location, author, dates, project number, client, department, discipline.
  • Describe content: design topic, element type, material, limit state, design code and edition.
  • Group identical copies and near-copies, and identify the latest or most complete version.
  • Separate calculations from non-calculations (quantities, templates, timesheets, scratch files).
  • Keep the catalogue current as new projects produce new files.

Blockers and risks

  • Access rights and confidentiality: client data, NDAs, restricted projects. Scanning needs legal and IT approval.
  • Volume: possibly hundreds of thousands of files; content analysis has a cost per file.
  • Poor metadata: authors have left, dates are reset on copy, project numbers exist only in folder names.
  • Old binary formats (early Mathcad, .xls) can only be opened by the original software.
  • Files stored outside managed locations (local disks, email attachments) are invisible.

Possible solutions

  • Read-only crawler over file shares and document management, combined with language-model classification of each file's content.
  • Derive project, client and discipline from folder conventions and the company project register.
  • Content fingerprints to group exact copies; similarity scoring to group near-copies.
  • Start with a curated pilot (one discipline, one topic such as shear design) before crawling everything.
  • A simple submission route for new files, with a short metadata form.

Questions for the workshop

  • Crawl everything automatically, or curate a selection? Or crawl for the catalogue and curate for conversion?
  • Who grants access to project data, and which areas stay off-limits?
  • What minimum metadata must a file have before it can be used?

catalogue of files with provenance and content description

2

Layer 2 · Normalisation

Conversion to a machine-readable form

↑ overview

Every file is translated into one structured representation that software and AI can read: the inputs, the formulas, the values, the units, the explanatory text, the figures, and a link from each item back to the exact place in the original. The aim is to capture the logic of the calculation, not a picture of its results.

InputCatalogued files in their native formats
OutputThe same content in one structured form, verified against the original's values

What has to be solved

  • Read the formulas and their dependencies (Excel cell references, Mathcad equations, code), not only the displayed numbers.
  • Preserve units, descriptions, code references, assumptions and sketches.
  • Keep traceability to the origin: sheet and cell, worksheet region, line of code.
  • Handle macros, table lookups, hidden sheets, links between workbooks and values typed over formulas.
  • Prove the conversion is faithful: recompute and compare every value with the one stored in the original.

Blockers and risks

  • Early Mathcad files are a closed binary format and need batch conversion through Mathcad itself.
  • Excel logic hidden in macros, goal-seek, data tables and manual overrides.
  • Mathcad carries units; Excel does not. Units live in labels and in hand conversions such as ×1000.
  • Hand calculations and scanned PDFs exist only as images; text recognition of equations is unreliable.
  • The target format is not yet agreed (see below).

Possible solutions

  • Format-specific readers: Excel formulas can be read directly; Mathcad Prime files are XML inside a compressed package; notebooks and scripts are text.
  • Language-model assistance to interpret messy, unlabelled sheets, with every number recomputed deterministically and compared with the original.
  • A units engine that tracks physical dimensions, so N, kN and N/mm² cannot be confused.
  • A neutral intermediate description (inputs, equations, checks) that does not depend on the final programming language.

Questions for the workshop

  • Which target format? Python is the working assumption, but it is open for debate.
  • What do we do with files that cannot be converted faithfully: re-model by hand, or leave out?
  • Is a match with the original's values enough proof, given the original may itself be wrong?

Point of contention · target format

Python is the working assumption: plain text, version-controllable, widely known, with mature libraries for units, symbolic mathematics and plotting. No need to reinvent the wheel. The alternatives deserve a fair hearing, and the answer may be a combination.

OptionStrengthsWeaknesses
Python codeExecutable, modular, testable, diff-able in version control; large engineering ecosystem; freeNot readable by non-programmers without a report layer; needs coding discipline and test practice
Structured data (JSON / YAML schema)Language-neutral, easy to validate and compare; good as the intermediate representationSomething else still has to execute the logic; procedures and iterations are awkward to express
Relational database (SQL)Excellent for the catalogue, metadata, results and queries across projectsPoor at expressing and versioning calculation logic
Notebooks (Jupyter)Narrative, equations and code in one document, close to the Mathcad experienceHidden execution state, hard to review and reuse as modules
Compiled languages (C++ / C#)Fast, robust, good for integration with commercial softwareSlower to develop, fewer engineers can read it; rarely needed for design checks
Keep Excel / MathcadEveryone can use them today; no retrainingDuplication, weak version control, logic locked inside files: the problem we are trying to solve

structured content of each file, traceable to its origin

3

Layer 3 · Extraction and classification

Decomposition into calculation units

↑ overview

The AI breaks each file down into calculation units: self-contained pieces of design logic, each covering one design concept with its inputs, equations, code coefficients, verification criterion and code reference. Generic design logic is separated from project data (geometry, loads, materials) and from presentation (layout, formatting). The units are then classified and clustered by design topic.

InputThe structured content of one file
OutputCandidate calculation units, classified and linked to code clauses

Example

One spreadsheet titled "RC beam design" is found to contain four design concepts and a block of project data:

Shear resistance VRd,c / VRd,s Torsion TRd,max Shear–torsion interaction Crack width wk Longitudinal bending MRd Project data: geometry, loads, materials

What has to be solved

  • Find the boundaries of each design concept, even when several are interleaved on one sheet.
  • Separate generic logic from project data and from formatting.
  • Classify each unit: design topic, element type, limit state, material, code, clause, equation number, national annex.
  • Recognise the same equation written with different symbols or rearranged (VEd versus Vsd).
  • Map dependencies: which quantities feed which results and checks.
  • Separate noise: unused cells, scratch work, superseded or duplicated blocks.

Blockers and risks

  • Topics and load cases are mixed in one grid; logic is spread over several tabs.
  • Symbols differ between engineers and between code editions (EN 1992-1-1:2004 versus the second generation).
  • Office rules of thumb and simplifications that appear in no code: knowledge or noise?
  • A wrong classification at this stage carries into the knowledge base.

Possible solutions

  • Dependency analysis of formulas: each chain that ends in a result or a check is a natural unit.
  • Structural comparison of equations, independent of the symbol names used.
  • Classification by language model against a controlled vocabulary of topics, elements and code clauses.
  • A company naming convention for symbols, following Eurocode notation, with a synonym list.
  • Engineers confirm classifications at first; automate once accuracy has been measured.

Questions for the workshop

  • What is the right size of a unit: one equation, one code clause, or one complete design check?
  • Who defines and maintains the classification vocabulary?

Layer 4 · Reconciliation

Consolidation into the single source of truth

↑ overview

Each candidate unit is compared with the master module for its design concept. Only what is new or what corrects the master is merged; duplicates are linked as further evidence; errors are rejected and flagged. The master is not rewritten every time a file arrives, only when the comparison shows it matters. Every accepted or rejected change is recorded with the reason and the person who approved it.

InputCandidate units from many files, plus corrections from project use
OutputOne master module per design concept, with a recorded history of changes

Example · ten shear design sheets

7 identical or equivalent → linked as evidence 2 include axial force → extension merged 1 uses a wrong reinforcement ratio limit → rejected, flagged

Result: one master shear module, now covering axial force, backed by nine sources and one recorded rejection.

What has to be solved

  • Classify each difference from the master: identical, equivalent (same result, different form), variant (other national annex, method or code edition), extension (adds scope), conflict (different result), or error.
  • Merge only extensions and corrections; never duplicate existing logic.
  • Detect mistakes instead of absorbing them, by checking against the code text and benchmark cases.
  • Keep legitimate variants side by side (national annexes, code editions).
  • Decide who may approve which changes, and record the decision.

Blockers and risks

  • When sources disagree, deciding which is correct. A majority of sheets is not proof.
  • Different code interpretations between offices and countries.
  • Early pollution: the master starts from unverified material.
  • Reviewer capacity: many candidates, few senior engineers.

Possible solutions

  • Automatic handling only for identical and equivalent units; every other class goes to a reviewer.
  • A library of benchmark cases (worked examples from codes and textbooks, verified software, checked past projects) that every candidate must reproduce.
  • Change proposals handled like a drawing revision: prepared, checked, approved.
  • A confidence rating per module that rises with independent sources, benchmarks passed and approvals.

Questions for the workshop

  • Who has authority to approve changes to a master, per discipline?
  • How many independent sources and benchmarks before a module counts as verified?
  • How much supervision do we accept at each stage (table below)?

Layer 5 · Infrastructure

Hosting, version control and governance

↑ overview

The knowledge base needs a secure, scalable home where every revision is kept, access is controlled, and every change is reviewed and automatically re-tested. The rules that the AI gatekeeper follows (how new logic must be structured, named, referenced and tested) are written down in plain language and stored with the library, so engineers and AI work to the same rules.

InputMaster modules, their history and the benchmark cases
OutputA versioned, auditable library that every office can use

What has to be solved

  • Version control: who changed what, when and why; any earlier revision recoverable; which projects used which revision.
  • Access control: who can read, who can propose, who can approve.
  • Data protection: client data stays inside the company; where the AI runs and where data is processed.
  • Written rules for the AI gatekeeper and for contributors: structure, naming, units, code references, tests, acceptance criteria.
  • Continuous verification: every change re-runs all benchmark cases; nothing is merged while a benchmark fails.
  • Scale: thousands of modules, many users, several offices.

Blockers and risks

  • IT and security approval for AI services and for central storage of design logic.
  • Cost and licensing: AI usage, hosting, software licences needed for conversion.
  • Governance so heavy that engineers stop contributing.

Possible solutions

  • The company's enterprise version-control platform with a protected main line, review and approval rules, and automated test pipelines.
  • AI services hosted by the company, or under a contract that keeps data in a defined region and out of model training.
  • Short governance documents: contribution guide, naming and units convention, review checklist, acceptance criteria.
  • Released library versions (for example quarterly) for project use, with change notes.

Questions for the workshop

  • Which platform does IT already support and approve?
  • Should every issued calculation state the library version it used? (Recommended.)

verified modules, released as a library version

Layer 6 · Application

Tool assembly

↑ overview

Project tools, such as "RC beam: shear, torsion, crack width", are assembled from verified modules. A tool references modules instead of copying them, so a correction to a module improves every tool that uses it. The same modules are used when an engineer builds a new calculation from scratch.

InputVerified modules and project data
OutputProject calculation tools that engineers run with their own inputs

What has to be solved

  • Compose tools from modules without duplicating logic.
  • A clear interface: project inputs in, results and verdicts out, consistent units.
  • Run many elements and load cases at once and identify the governing case.
  • Make tools usable by engineers who do not program.
  • Enforce each module's scope and validity limits (for example, a formula valid only up to C50/60).
  • Exchange data with analysis software (internal forces, load combinations).

Blockers and risks

  • Adoption: engineers trust the sheets they built themselves.
  • Choice of user interface: web application, spreadsheet add-in, or notebook.
  • A tool used outside its scope without a warning.

Possible solutions

  • Tool templates that declare their scope and validity limits and warn when an input falls outside them.
  • Spreadsheets as a front end that call the central logic: Excel remains the interface, not the place where the logic lives.
  • Batch runs with a summary table of all cases and the governing case reported in full.

Questions for the workshop

  • Which interface first?
  • Which three tools would deliver the most value as a pilot?

a tool run: inputs, results and every intermediate step

Layer 7 · Output and verification

Calculation reporting and quality assurance

↑ overview

The central unsolved problem

Logic written for reuse is modular and efficient, but it does not read like a hand calculation. A checker needs to follow the calculation the way a Mathcad sheet or a well-built spreadsheet allows. Today the two are separate things, so they drift apart. The human-readable calculation must be produced from the executing logic itself, at the same time and one-to-one, the way Mathcad works, never rewritten statically afterwards.

InputA tool run
OutputA checked and approved calculation report, with the calculation data kept inside it

What has to be solved

  • Every step shown as formula, then values substituted with units, then result, with the code clause in the margin.
  • Pass or fail verdicts and utilisation shown clearly.
  • Produced by the same execution that computed the numbers: change an input and the report follows.
  • The company report format: title block, project data, prepared / checked / approved, revision, page numbers.
  • Narrative, assumptions and sketches in the right places.
  • Levels of detail: full derivation for the governing case, a summary table for the rest.
  • Independent checking, by people and by automated checks.
  • The calculation data kept inside the issued report so it can be reused later.

Blockers and risks

  • Readability against modularity: logic structured for reuse does not follow the order of a hand calculation.
  • Engineering conventions for symbols, subscripts, units, rounding and significant figures.
  • Checkers, clients and checking authorities are used to Mathcad and Excel output.
  • Professional responsibility: who signs a calculation prepared with AI assistance.

Possible solutions

  • Each module carries its own presentation (description, symbols, code clause, formula layout), printed automatically whenever it runs.
  • Symbolic mathematics that displays the evaluated expression with the numbers substituted. Existing open tools already do this, for example handcalcs and efficalc for Python, and Calcpad as a standalone application.
  • Literate calculation documents (narrative and live calculation together) exported to PDF.
  • Automated quality gates: unit and dimension checks, benchmark comparison, comparison with the original file, an AI reviewer reading the rendered report, then human checking and approval.

Questions for the workshop

  • What report format and level of detail will checkers and clients accept?
  • What must a human check, and what can be automated?
  • Which existing tools should we test first for the readable-output problem?

issued calculations in use on projects · issues reported back

Layer 8 · Continuous improvement

Feedback and maturity

↑ overview

At the start the knowledge base will hold many unverified calculations. Confidence grows through use: errors found on projects, checker comments and code revisions are proposed as corrections, pass through consolidation (stage 4) like any other change, and once approved they improve every tool that uses the module.

  1. HarvestedFound and catalogued. Not checked.
  2. ConvertedMachine-readable; reproduces the original's values.
  3. ConsolidatedMerged into a master; differences reviewed.
  4. VerifiedPasses all benchmark cases.
  5. ApprovedSigned off for project use.

What has to be solved

  • A simple way to report a problem from a project report back to the exact module and revision.
  • Corrections follow the same review and benchmark tests as any change.
  • Notify the projects that used an affected revision.
  • Track the maturity of every module and show it on the tools and reports that use it.
  • Handle new code editions (for example the second-generation Eurocodes) as new variants.

Blockers and risks

  • Engineers have no time or habit for reporting errors.
  • An error discovered in a module that issued calculations already relied on.
  • Maintenance depends on volunteers.

Possible solutions

  • An issue log linked to modules, reachable from every report.
  • A dashboard of modules, maturity, open issues and usage.
  • Named module owners per discipline, and recognition for contributors.

Questions for the workshop

  • Can an unverified module be used on a project at all, and if so, with what warning?
  • Who owns maintenance once the pilot is over?

Part 5

Concerns that cut across every stage

Confidentiality

Client data and project information must not leave approved systems. Decide what the AI may read, where it runs, and what is anonymised.

Professional responsibility

The signing engineer remains responsible. The system must make checking easier and must never hide how a result was obtained.

Codes and intellectual property

Design codes are copyrighted. Store clause references and our implementation, not the code text. Agree ownership of contributed logic.

Cost and resources

AI usage, hosting, licences and, above all, senior engineering time for review. A pilot gives real numbers.

Adoption and training

Engineers have to trust and use the tools. Start where the pain is largest, and show results early.

Measuring success

Duplicate sheets retired, modules verified, errors caught before issue, hours saved per check.
