Calculation Knowledge Architecture

RevisionC
Date2026-10-13

Problem

  • Thousands of calculation files on servers and project folders, in many formats.
  • The same checks are rebuilt on every project; copies diverge, corrections do not propagate.
  • Origin, author, code edition and quality are often unknown.
  • Excel and Mathcad are readable but hard to version and reuse; code is reusable but does not read as a calculation.

Objective

  • Extract the design logic from every calculation we own.
  • Merge it into one version-controlled library, organised by structural engineering topic, with gaps visible.
  • Produce tools and Mathcad-quality reports from that library.
  • Feed every correction and addition from projects back into it.

What has to be built, and how

Collect · 1

Retrieval and identification

An agent that scans the company servers and catalogues every calculation file.

  • Read-only access to servers and document systems
  • AI tags each file: project, department, author, date, code, design topics
  • New files and new calculations enter the same way
relevant topiccurrent codecompleteknown origincheckednot a duplicatefills a gap
MediumKnown technology; access rights, NDAs and volume are the hard part.
Collect · 2

Conversion

A reliable parser that converts each format into machine-readable content.

  • One reader per format: Excel, Mathcad, Python, Jupyter, MATLAB
  • AI to interpret unstructured sheets
  • Recalculate and compare with the original before accepting
HighMany formats and legacy files; reliability has to be proven.
Extract and unify · 3

Decomposition

An LLM that understands calculation logic, splits it into modular units and maps each unit to a design topic.

  • Design logic separated from project data
  • One taxonomy: topic, element, code clause
  • A topic map of structural engineering: what is covered, what is missing
HighNeeds engineering understanding and a consistent taxonomy.
Extract and unify · 4

Consolidation

An AI process that tests the extracted logic and merges units covering the same concept into one design method.

Every version is run over the same range of parameters, and the agreement decides how they are merged:

similarmerged automatically
partlydifferences blended in, engineer confirms
differentengineer decides; valid methods kept as alternatives
Very highThe core of the system. Agreement alone does not prove correctness.
Build and host · 5

Tool generation

An LLM that turns each unified method into a tested Python tool.

  • Written from a structured specification per module
  • Tested against benchmark cases and the original files
  • Engineer approves before release
MediumCode generation is mature; the test cases are the real work.
Build and host · 6

Central repository

A secure, version-controlled server with a searchable library.

  • Enterprise GitLab: versions, access rights, approvals
  • Written rules for contributors and for the AI
  • Search by topic, code and element
LowStandard practice; needs IT approval.
Use · 7

Calculation reports

A framework that prints Python calculations as readably as a Mathcad sheet.

  • Each step: equation, substituted values, result, clause
  • Generated by the same run that computes the numbers
  • Company template; QA status on the report
HighThe least solved part; partial solutions exist.
Use · 8

Review and feedback

A review process that feeds corrections and new components back into the library.

  • Users and checkers report errors or add components
  • Changes pass consolidation and testing again
  • Maturity: harvested → converted → consolidated → verified → approved
MediumMostly process, ownership and discipline.

Worked example: four bridge calculations

Four calculation files from four different bridge projects, each checking a reinforced concrete deck beam to EN 1992-1-1 and EN 1992-2.

FileFormatSourceTopics found
APython scriptBridge project 1Moment resistance, shear, crack width
BJupyter notebookBridge project 2Moment resistance, shear, crack width
CExcel workbookBridge project 3Moment resistance, shear, crack width
DMathcad sheetBridge project 4Moment resistance, shear, crack width, pier pile cap
  1. 1
    Retrieval and identification

    The agent finds the four files on four project servers and tags them with project, author, date, code and topics. All four meet the selection criteria.

  2. 2
    Conversion

    The parser converts each file to machine-readable content. Recalculated values match the originals.

  3. 3
    Decomposition

    Each file is split into units for moment resistance, shear and crack width. D's pile cap design adds foundation design to the topic map.

  4. 4
    Consolidation

    The four files check crack width for different scenarios (load cases, cover, bar sizes), so their results cannot be compared directly. The AI extracts each version's logic and runs all four over the same range of parameters.

    • similarMoment resistance: same results across the whole range. Merged.
    • partlyCrack width: A, B and D agree. C differs only for widely spaced bars, where it applies the alternative crack spacing rule of 7.3.4(3). Added to the unified logic as a branch; an engineer confirms.
    • differentShear: D uses a strut-and-tie model near the supports. Kept as an alternative method.

    The result is one structured specification per topic.

  5. 5
    Tool generation

    The LLM writes a Python tool from each specification. It is tested over the same parameter range against the four originals and against benchmark cases.

  6. 6
    Central repository

    Stored on GitLab as version 0.1, searchable under "crack width, concrete deck".

  7. 7
    Calculation reports

    An engineer on a fifth bridge project runs the tool. The report shows every step as equation, values, result and clause, like a Mathcad sheet. A checker reviews it.

  8. 8
    Review and feedback

    The checker adds a new component, the minimum reinforcement check of 7.3.2. It passes consolidation and testing and is released as version 0.2. The next project starts from 0.2.
