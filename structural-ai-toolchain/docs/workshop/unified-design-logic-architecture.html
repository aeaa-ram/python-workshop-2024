Workshop basis

Unified Design Logic Architecture

StatusIssued for workshop
RevisionG
Date2026-11-15

Problem

  • Calculations are spread across servers and project folders in many formats. Their origin, author, code edition and quality are often unknown.
  • The same checks are rebuilt on every project. The versions are not connected, so a correction made in one is not carried to the others and the same errors are repeated.
  • Many calculations are incomplete: assumptions, limits of validity and references to the design code are missing.
  • Spreadsheets are easy to read but hard to version and reuse; code is reusable but does not read as a calculation.

Objective

A knowledge base that holds one verified design logic for each topic of structural engineering. From this single logic we can create customisable calculation reports, engineering tools such as spreadsheets and calculation sheets, and AI-assisted tools, all giving the same results.

The knowledge base is built by a pipeline that retrieves the calculations we own, distils the design logic in them, compares it with the design codes and consolidates it under engineer review. It is version-controlled, shows which topics are covered and where the gaps are, and improves with every project that uses it.

Components

Ingestion · 1

Retrieval and curation

Retrieves calculations and reports from existing project databases and curates the files that enter the pipeline.

  • Searches project databases, servers and document systems
  • Records for each file: project, department, author, date, design code and design topics
  • Removes duplicates and superseded versions; keeps files that are relevant, complete, of known origin and to a current code edition
  • New calculations enter through the same route
Ingestion · 2

Conversion

Parses each document into a machine-readable format from which the computer can recreate the original values.

  • Readers for Excel, Mathcad, Word, PDF, Python and Jupyter; scanned documents are read by text recognition
  • Each converted file is recalculated and compared with the values in the original before it is accepted
Distillation · 3

Decomposition

An AI that distils each file into modular calculation objects and maps them to the design topics, using a framework pre-mapped from the design codes.

  • Design logic separated from project data
  • The framework is mapped from the Eurocodes in advance: topic, element, clause, expression and nationally determined parameters
  • Each object is compared with the code: as in the code, simplified, alternative or different
  • A topic map: what is covered, what is missing, where sources are many

Human review. An engineer checks the extracted objects and their classification. Drafts never enter the knowledge base.

Distillation · 4

Consolidation

Deterministic consensus rules that merge the objects from many sources into one unified design logic per topic.

Each object is evaluated over a common, sampled parameter domain. Sources whose results converge within a tolerance are merged, so one logic is reviewed instead of many. Where results do not converge, the cause is identified, such as a simplification, a unit or a misread value, or the difference is referred to an engineer.

Agreement between sources is not proof of correctness. Accuracy is established by benchmarks against independent references: code worked examples, design guides, hand calculations and FE results.

Human review. An engineer reviews each unified logic and settles every disagreement.

Knowledge base · 5

Object generation

Turns each unified design logic into a tested calculation object.

  • Written in Python from a structured specification per object
  • Benchmarked against the original files, other checked projects and independent references

Human review. An engineer signs off each block before it enters the knowledge base; full review at first, sampling once confidence is established.

Knowledge base · 6

Repository and search

A secure, version-controlled knowledge base with an AI-curated search engine.

  • Finds the relevant calculation object for a design task
  • Checks every new calculation: already covered, an extension, or a new design topic
  • Versions, access rights, approvals and written rules for contributors and the AI
Use and maintenance · 7

Calculations, reports and tools

Produces calculations, reports and tools from the same verified logic.

  • Self-documenting calculations: equation, substituted values, result and clause for each step, at the quality of our existing calculations
  • Customisable reports over many design cases, in the company template, as PDF or Word
  • Engineering tools: spreadsheets and Mathcad sheets with live formulas
  • AI-assisted tools that use the same calculation objects
  • Every output carries the version of the logic it was made from; signed off by the project engineer and checker, as today
Use and maintenance · 8

Maintenance

Auditing of the knowledge base, scheduled health checks, and a route for corrections and new components.

  • Health checks re-run every benchmark
  • Corrections and new components pass consolidation and testing again, and are released as a new version
  • Maturity of each object: retrieved, converted, consolidated, verified, approved

Human review. Engineers review calculations in use and approve every correction and new component.

Worked example: four bridge calculations

Four files from four bridge projects. They overlap only partly and use different national annexes.

FileFormatProjectBendingShearNational annex
APython scriptBridge 1✓✓DK
BJupyter notebookBridge 2✓–UK
CExcel workbookBridge 3–✓DK
DMathcad sheetBridge 4✓✓NO
  1. 1
    Retrieval and curation

    The four files are found in the project databases and tagged with project, author, date and design code. Two older copies of file C are removed as duplicates.

  2. 2
    Conversion

    The four files are converted and recalculated. The recalculated values match the originals.

  3. 3
    Decomposition

    Six calculation objects are drafted: three for bending (A, B, D) and three for shear (A, C, D), each mapped to its clause in the code framework. An engineer checks them.

  4. 4
    Consolidation

    Bending: the national annex coefficients are separated out as parameters, after which the three objects converge over the whole domain and are merged into one, with the national annex as an input. Shear: the objects use different lever arms, one approximate and one calculated. The rest of the logic converges and is merged; an engineer decides which lever arm is correct.

  5. 5
    Object generation

    Python objects are generated and benchmarked against the four original files, other checked bridge projects and a code worked example. An engineer signs off each object.

  6. 6
    Repository and search

    The objects are released as version 0.1. An engineer on a fifth bridge searches for shear design and is given the unified object.

  7. 7
    Calculations, reports and tools

    The engineer runs the object for every girder and receives a self-documenting report, and a spreadsheet for the checker, both from the same version.

  8. 8
    Maintenance

    A torsion calculation is submitted. The search identifies it as a new component; it passes consolidation and the benchmarks, an engineer signs it off, and it is released as version 0.2. Every health check re-runs the benchmarks of all four projects.
